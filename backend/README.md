# PostureGuard study server

Receives finished sessions from the app and participant registrations from
the onboarding form, and stores them for analysis. The session request
format is [`study/API_SCHEMA.md`](../study/API_SCHEMA.md).

FastAPI + SQLAlchemy. PostgreSQL in deployment, SQLite for local development
and tests.

| Endpoint | What it does |
|---|---|
| `POST /api/sessions` | Stores one session: summary, per-second events, device metrics |
| `POST /api/participants` | Stores one onboarding form submission |
| `GET /onboarding` | Serves the onboarding form (`study/participant_onboarding.html`) |
| `GET /health` | Returns `{"ok": true}` |

## Deployment

Hosted by Sapienza at `https://postureguard.test.sapienzaapps.it`. Their
reverse proxy, on the same machine, terminates HTTPS and forwards to the API
on `127.0.0.1:8000`.

```bash
git clone https://github.com/MartheNashaat/PostureGuard2025_2026_MartheElgawly2170201__BeyzaNurElaslan_2180876.git postureguard
cd postureguard/backend
cat > .env <<'EOF'
POSTGRES_PASSWORD=<a long random password>
REQUIRE_REGISTERED_USER=true
EOF
docker compose up -d --build
curl http://127.0.0.1:8000/health        # {"ok":true}
```

What the reverse proxy needs:

- Forward `postureguard.test.sapienzaapps.it` to `http://127.0.0.1:8000`.
- Allow request bodies up to 5 MB (a session upload is a few hundred KB).
- Only the API goes through the proxy. PostgreSQL has no published port and
  stays inside the compose network.

**Updating** after a change is merged: `git pull`, then
`docker compose up -d --build`. The database volume is kept. Tables are
created on startup if missing; existing tables are never altered, so a
change to an existing table needs a manual migration.

### Settings (`backend/.env`)

| Variable | Meaning |
|---|---|
| `POSTGRES_PASSWORD` | Required. The database password. |
| `REQUIRE_REGISTERED_USER` | `true` (the default in Docker) refuses sessions whose `user_id` has no registration (`422`). Test devices must register their test ID on the form first. Unset when running uvicorn locally, so local development accepts any ID. |

## Run locally

```bash
cd backend
python3 -m venv .venv
.venv/bin/pip install -r requirements-dev.txt
.venv/bin/uvicorn app.main:app --reload
```

The server listens on `http://127.0.0.1:8000` and writes to
`backend/postureguard.db` (SQLite). Set `DATABASE_URL` to use PostgreSQL
instead. The form is at `http://127.0.0.1:8000/onboarding`.

## Tests

```bash
cd backend
.venv/bin/python -m pytest
```

The payloads in `tests/fixtures/` were generated by the app's own
`buildSessionPayload` and integrity check, so the tests check the server
against what the phone really sends. Regenerate them when the payload changes.

## What the server accepts

### Sessions

| Case | Response |
|---|---|
| Clean session (`integrity.is_valid: true`) | `200 {"ok": true}` |
| Gap-only session (`is_valid: false`, `gap_count > 0`) | `200 {"ok": true}`, stored with `is_valid = false` |
| Same `(user_id, session_id)` again — a retry | `200 {"ok": true, "duplicate": true}`, first copy kept |
| Bad `user_id` (not 6–20 letters/numbers) or `variant` (not A, B or C) | `422` |
| Events not in strictly increasing time order | `422` |
| `is_valid: false` with `gap_count: 0`, or `missing_count > 0` | `422` — only gap-only sessions may be uploaded as invalid |
| No events | `422` |
| `user_id` not registered, with `REQUIRE_REGISTERED_USER=true` | `422` — exact match, case included |

`variant` `C` is accepted so internal test sessions can be uploaded; it is
hidden from participants and excluded from analysis.

Sessions are keyed by `(user_id, session_id)`: `session_id` is the session's
start time and only unique per phone.

### Registrations

| Case | Response |
|---|---|
| Valid submission | `200 {"ok": true}` |
| `user_id` already registered, ignoring case | `409 {"ok": false, "error": "duplicate user_id"}` — the form asks for another ID |
| Bad `user_id` | `422 {"ok": false, "error": "invalid user_id"}` |
| A required consent not given, age under 18, name/email/signature missing | `422 {"ok": false, "error": "<reason>"}` |

## Tables

- `sessions` (one row per session, device-metrics summary flattened in),
  `posture_events` (one row per second), `device_metrics` (one row every
  15 s).
- `participants`: consent and demographics from the form, one row per
  participant.
- `participant_identities`: name, email, signature and date — the
  **restricted linking list**, needed for withdrawal requests. Nothing else
  references it, and the export leaves it out by default.

## During and after the study

```bash
docker compose exec api python -m scripts.status
```

Prints sessions whose `user_id` matches no registration (and whether only
the capitalisation differs), participants who used more than one variant,
registered participants with no sessions yet, the A/B split and each
participant's session count. Run it regularly while the study runs.

```bash
docker compose exec api python -m scripts.export /srv/export
docker compose cp api:/srv/export ./export
```

Writes `sessions.csv`, `posture_events.csv`, `device_metrics.csv` and
`participants.csv`, joined on `user_id`. Variant C sessions are left out
(`--include-test` keeps them). `--with-identities` also writes
`identities.csv`; keep that file apart from the research data.
